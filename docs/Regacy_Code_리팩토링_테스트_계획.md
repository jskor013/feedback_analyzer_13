# Regacy Code 리팩토링 테스트 계획

## 1. 목적

이 문서는 Feedback Analyzer C++ 코드의 리팩토링을 안전하게 진행하기 위한 테스트 계획이다. 기존 코드는 변경하지 않고, 현재 동작을 보존해야 하는 영역과 현재 버그로 인해 실패가 예상되는 영역을 구분한다.

테스트 계획의 목표는 다음과 같다.

- 현재 정상 동작을 Golden Master Test로 고정한다.
- 현재 코드에서 오동작이 예상되는 RED CASE를 명확히 기록한다.
- 리팩토링 각 1커밋 단계마다 어떤 테스트가 Green으로 바뀌어야 하는지 정의한다.
- 리팩토링 중 기능 회귀와 의도하지 않은 동작 변경을 조기에 발견한다.

## 2. 테스트 전략

### 2.1 테스트 분류

Golden Master Test:

- 현재 코드에서 정상으로 간주되는 동작을 기록한다.
- 리팩토링 중 기존 사용자 흐름이 깨지지 않았는지 확인한다.
- 현재 코드의 모든 결함을 정답으로 고정하지 않는다.
- 정상 입력, 정상 업로드, 정상 필터링, 정상 다운로드 같은 기본 흐름을 대상으로 한다.

RED CASE:

- 현재 코드에서 버그 또는 구조적 한계로 인해 실패하거나 오동작할 것으로 예상되는 테스트이다.
- 리팩토링 전에는 실패가 정상이다.
- 관련 커밋이 완료되면 Green으로 전환되어야 한다.

Refactoring Test:

- 각 1커밋 리팩토링 단계에서 추가하거나 활성화할 테스트이다.
- 해당 커밋의 완료 기준을 판단하는 테스트이다.
- 경계조건, 오류 입력, 상태 오염, 기준 불일치, CSV 특수문자 등을 포함한다.

### 2.2 테스트 레벨

수동 시나리오 테스트:

- 현재 구조에서 자동화가 어려운 HTTP 화면 흐름을 검증한다.
- 리팩토링 초기 단계에서 Golden Master 용도로 사용한다.

통합 테스트:

- 입력, 분석, 필터, 다운로드가 연결된 흐름을 검증한다.
- 상태 오염과 회귀를 확인하는 데 사용한다.

단위 테스트:

- 리팩토링 후 분석, 필터링, CSV 처리, 입력 검증을 독립적으로 검증한다.
- Commit 10 이후부터 본격적으로 확대한다.

회귀 테스트:

- RED CASE가 Green으로 바뀐 뒤 다시 실패하지 않도록 고정한다.
- 버그 수정 커밋마다 관련 테스트를 회귀 테스트 목록에 추가한다.

## 3. 테스트 데이터 기준

### 3.1 기본 피드백 데이터

다음 데이터는 Golden Master와 리팩토링 테스트의 공통 기준 데이터로 사용한다.

- 긍정 배송 피드백: 배송이 빠르고 서비스가 좋아요
- 부정 배송 피드백: 배송지연 때문에 너무 불편하고 실망했습니다
- 가격 피드백: 가격이 저렴하고 가성비가 좋아요
- 품질 피드백: 제품 품질이 좋고 마감이 훌륭합니다
- 서비스 피드백: 상담 응대가 친절해서 만족합니다
- 사용성 피드백: 사용법이 어렵고 설명서가 불편합니다
- 중립 피드백: 제품을 오늘 받았습니다

### 3.2 CSV 정상 데이터

정상 CSV는 다음 조건을 만족해야 한다.

- 첫 줄에 텍스트 컬럼 헤더가 있다.
- 텍스트 컬럼에 비어 있지 않은 피드백이 있다.
- 한 줄에 하나의 피드백이 들어 있다.
- UTF-8 텍스트가 깨지지 않는다.

### 3.3 CSV 경계 데이터

경계 데이터는 다음 케이스를 포함한다.

- 헤더가 없는 CSV
- 텍스트 컬럼이 첫 번째가 아닌 CSV
- 빈 파일
- 텍스트 값이 비어 있는 행
- 쉼표가 포함된 피드백
- 따옴표가 포함된 피드백
- 줄바꿈이 포함된 피드백
- 컬럼 수가 행마다 다른 CSV

## 4. Golden Master Test

Golden Master Test는 현재 정상 동작을 보존하기 위한 테스트이다. 리팩토링 중 아래 시나리오는 계속 통과해야 한다.

### GM-01. 초기 화면 표시

목적:

- 애플리케이션 시작 후 기본 화면이 표시되는지 확인한다.

절차:

- 서버를 실행한다.
- 브라우저로 기본 화면에 접속한다.

기대 결과:

- 피드백 입력 영역이 표시된다.
- CSV 업로드 영역이 표시된다.
- 감정 필터 선택지가 표시된다.
- 카테고리 필터 선택지가 표시된다.
- 오류 화면이 표시되지 않는다.

### GM-02. 단일 피드백 직접 입력

목적:

- 사용자가 텍스트를 직접 입력했을 때 분석 대상에 추가되는지 확인한다.

절차:

- 긍정 배송 피드백을 입력한다.
- 분석 결과 화면을 확인한다.

기대 결과:

- 입력한 피드백 개수가 1개로 표시된다.
- 감정 분석 결과에 긍정 항목이 표시된다.
- 키워드 또는 카테고리 분석 결과에 관련 항목이 표시된다.

### GM-03. 여러 피드백 누적 입력

목적:

- 여러 피드백이 누적되어 분석되는 현재 동작을 보존한다.

절차:

- 긍정 배송 피드백을 입력한다.
- 부정 배송 피드백을 추가 입력한다.
- 가격 피드백을 추가 입력한다.

기대 결과:

- 전체 피드백 개수가 누적되어 표시된다.
- 긍정과 부정 결과가 함께 표시된다.
- 여러 카테고리 결과가 함께 표시된다.

### GM-04. 정상 CSV 업로드

목적:

- 정상 형식의 CSV 업로드가 기존처럼 처리되는지 확인한다.

절차:

- 텍스트 컬럼을 포함한 정상 CSV를 업로드한다.
- 업로드 후 화면 메시지와 피드백 개수를 확인한다.

기대 결과:

- CSV의 피드백이 분석 대상에 추가된다.
- 업로드 후 오류가 표시되지 않는다.
- 피드백 개수가 업로드 데이터 수와 일치한다.

### GM-05. 감정 필터 정상 동작

목적:

- 감정 필터가 현재 정상 입력 데이터에서 동작하는지 확인한다.

절차:

- 긍정, 부정, 중립 피드백을 입력한다.
- 긍정 필터를 실행한다.
- 부정 필터를 실행한다.

기대 결과:

- 긍정 필터에서는 긍정으로 판단되는 피드백만 표시된다.
- 부정 필터에서는 부정으로 판단되는 피드백만 표시된다.
- 필터 결과가 있는 경우 분석 결과 영역이 표시된다.

### GM-06. 카테고리 필터 정상 동작

목적:

- 카테고리 필터가 대표적인 정상 데이터에서 동작하는지 확인한다.

절차:

- 배송, 가격, 품질, 서비스, 사용성 관련 피드백을 입력한다.
- 각 카테고리 필터를 실행한다.

기대 결과:

- 선택한 카테고리와 관련된 피드백이 표시된다.
- 다른 카테고리 피드백이 과도하게 섞이지 않는다.

### GM-07. 필터 결과 다운로드

목적:

- 필터 결과가 있는 상태에서 다운로드가 정상 동작하는지 확인한다.

절차:

- 여러 피드백을 입력한다.
- 특정 필터를 실행해 결과를 만든다.
- 결과 다운로드를 실행한다.

기대 결과:

- 다운로드 파일이 생성된다.
- 파일에는 필터 결과에 해당하는 피드백이 포함된다.
- 파일 인코딩이 한국어를 표현할 수 있어야 한다.

### GM-08. HTML 기본 이스케이프

목적:

- 기본적인 특수문자 입력이 화면을 깨뜨리지 않는지 확인한다.

절차:

- 꺾쇠괄호와 따옴표가 포함된 텍스트를 입력한다.
- 결과 화면을 확인한다.

기대 결과:

- 입력 텍스트가 화면 구조를 깨뜨리지 않는다.
- 브라우저에서 스크립트나 태그로 실행되지 않는다.

## 5. RED CASE

RED CASE는 현재 코드에서 실패하거나 오동작이 예상되는 테스트이다. 리팩토링 전에는 실패 상태를 기록하고, 관련 커밋에서 Green으로 전환한다.

### RED-01. 필터 결과 없음 이후 이전 다운로드 결과 재사용

관련 커밋:

- Commit 1
- Commit 2

절차:

- 결과가 있는 필터를 실행한다.
- 다운로드가 가능한 상태를 만든다.
- 결과가 없는 필터 조건을 실행한다.
- 다시 다운로드를 실행한다.

현재 예상 결과:

- 이전 필터 결과가 그대로 다운로드될 수 있다.

Green 기대 결과:

- 결과가 없는 필터 이후에는 이전 다운로드 결과가 재사용되지 않는다.
- 다운로드가 차단되거나 빈 결과임이 명확히 표현된다.

### RED-02. 필터 전 다운로드

관련 커밋:

- Commit 1
- Commit 2

절차:

- 서버를 시작한다.
- 필터를 실행하지 않는다.
- 다운로드를 바로 실행한다.

현재 예상 결과:

- 비어 있는 파일이 생성되거나 다운로드 의미가 불명확하다.

Green 기대 결과:

- 다운로드할 결과가 없음을 명확히 알려준다.
- 이전 실행의 데이터가 섞이지 않는다.

### RED-03. 사용자 간 데이터 혼합

관련 커밋:

- Commit 2
- Commit 3

절차:

- 사용자 A가 피드백을 입력한다.
- 사용자 B가 다른 브라우저 또는 세션으로 접속한다.
- 사용자 B가 분석 또는 다운로드를 실행한다.

현재 예상 결과:

- 사용자 A의 데이터가 사용자 B에게 보일 수 있다.

Green 기대 결과:

- 사용자별 데이터 경계가 명확하다.
- 공유 데이터라면 그 의도가 명확히 표현되고 동시 접근 정책이 적용된다.

### RED-04. 분석 결과와 감정 필터 결과 불일치

관련 커밋:

- Commit 4
- Commit 12

절차:

- 감정 키워드가 분석 기준과 필터 기준에서 다르게 처리될 수 있는 문장을 입력한다.
- 전체 분석 결과를 확인한다.
- 같은 감정 필터를 실행한다.

현재 예상 결과:

- 분석 결과와 필터 결과가 서로 다르게 보일 수 있다.

Green 기대 결과:

- 같은 피드백에 대해 분석과 필터가 동일한 감정 판단을 사용한다.

### RED-05. 카테고리 분석과 카테고리 필터 불일치

관련 커밋:

- Commit 5
- Commit 12

절차:

- 대표 카테고리 키워드만 포함된 피드백을 입력한다.
- 분석 결과에서 카테고리 포함 여부를 확인한다.
- 동일 카테고리 필터를 실행한다.

현재 예상 결과:

- 분석에는 포함되지만 필터에서는 빠질 수 있다.

Green 기대 결과:

- 분석과 필터가 동일한 카테고리 판단 기준을 사용한다.

### RED-06. 헤더 없는 CSV 첫 데이터 유실

관련 커밋:

- Commit 6
- Commit 11

절차:

- 헤더 없이 첫 줄부터 피드백이 있는 CSV를 업로드한다.

현재 예상 결과:

- 첫 번째 피드백이 헤더로 간주되어 유실될 수 있다.

Green 기대 결과:

- 헤더가 없는 파일은 명확히 오류 처리되거나 정책에 따라 모든 행을 데이터로 처리한다.
- 어떤 방식이든 조용한 데이터 유실은 없어야 한다.

### RED-07. 텍스트 컬럼 위치 변경 시 잘못된 컬럼 분석

관련 커밋:

- Commit 6
- Commit 11

절차:

- 첫 번째 컬럼은 ID이고 두 번째 컬럼이 텍스트인 CSV를 업로드한다.

현재 예상 결과:

- 첫 번째 컬럼 값이 피드백으로 분석될 수 있다.

Green 기대 결과:

- 텍스트 컬럼명을 기준으로 올바른 값을 읽는다.
- 필수 컬럼이 없으면 명확한 오류를 표시한다.

### RED-08. 쉼표 포함 CSV 필드 처리 오류

관련 커밋:

- Commit 7
- Commit 11

절차:

- 쉼표가 포함된 피드백을 CSV로 업로드한다.
- 분석 결과와 다운로드 결과를 확인한다.

현재 예상 결과:

- 텍스트가 여러 컬럼으로 잘못 분리될 수 있다.

Green 기대 결과:

- 쉼표가 포함된 텍스트가 하나의 피드백으로 유지된다.

### RED-09. 따옴표 포함 CSV 필드 처리 오류

관련 커밋:

- Commit 7
- Commit 11

절차:

- 따옴표가 포함된 피드백을 CSV로 업로드한다.
- 다운로드 후 다시 열어본다.

현재 예상 결과:

- 따옴표가 사라지거나 필드 구조가 깨질 수 있다.

Green 기대 결과:

- 따옴표가 CSV 규칙에 맞게 보존된다.

### RED-10. 줄바꿈 포함 CSV 필드 처리 오류

관련 커밋:

- Commit 7
- Commit 11

절차:

- 줄바꿈이 포함된 피드백을 CSV로 업로드한다.
- 다운로드 파일의 행 구조를 확인한다.

현재 예상 결과:

- 하나의 피드백이 여러 행으로 잘못 분리될 수 있다.

Green 기대 결과:

## 8. 최종 승인 기준

리팩토링 완료 시 다음 조건을 만족해야 한다.

- Golden Master Test가 모두 통과한다.
- RED CASE가 모두 Green으로 전환된다.
- Green으로 전환된 RED CASE가 회귀 테스트로 유지된다.
- CSV 입력과 출력 테스트가 정상 데이터와 경계 데이터를 모두 포함한다.
- 분석과 필터 결과가 동일한 기준을 사용한다.
- 반복 테스트 실행 시 상태 오염이 발생하지 않는다.
- 실패 상황이 사용자에게 성공으로 표시되지 않는다.
- 서버 시작 실패와 처리 오류가 로그로 확인 가능하다.

## 9. 테스트 실행 순서 제안

리팩토링 전:

1. Golden Master Test를 수동으로 실행해 현재 정상 동작을 기록한다.
2. RED CASE를 실행해 현재 실패 또는 오동작을 재현한다.
3. 실패 결과를 버그 기준선으로 남긴다.

각 커밋 후:

1. 해당 커밋의 필수 테스트를 실행한다.
2. 이전 커밋에서 Green이 된 RED CASE를 회귀 테스트로 다시 실행한다.
3. 관련 Golden Master Test를 실행한다.
4. 실패가 발생하면 기능 변경인지 회귀인지 구분한다.

리팩토링 완료 후:

1. 전체 Golden Master Test를 실행한다.
2. 전체 RED CASE 회귀 테스트를 실행한다.
3. 전체 단위 테스트와 통합 테스트를 실행한다.
4. 수동 화면 테스트로 사용자 흐름을 최종 확인한다.

## 10. 주의사항

- Golden Master Test는 현재 정상 동작 보존용이며, 알려진 버그까지 영구 보존하기 위한 테스트가 아니다.
- RED CASE는 리팩토링 전 실패가 정상이며, 관련 커밋 완료 후 Green으로 전환되어야 한다.
- 구조 분리 커밋에서는 기능 변화가 최소화되어야 한다.
- 버그 수정 커밋에서는 어떤 RED CASE가 Green으로 바뀌는지 명확히 기록해야 한다.
- 테스트 추가 커밋에서는 테스트 안정성을 위해 전역 상태 오염 여부를 반드시 확인해야 한다.
