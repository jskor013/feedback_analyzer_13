# PRD: Phase 4 운영 안정성 개선

## 1. 프로젝트 개요

### 1.1 한 줄 목적문

Feedback Analyzer 사용자가 서버 시작 실패와 로그 노출 위험 없이 안정적으로 피드백 분석 기능을 사용할 수 있도록 운영 안정성을 강화한다.

### 1.2 배경 및 문제 정의

현재 코드는 단일 `main` 중심 구조에 요청 처리, 화면 출력, 분석 호출, 필터링, 다운로드, 로깅 흐름이 집중되어 있다.

운영 안정성 관점의 핵심 문제는 다음과 같다.

- 서버가 포트 바인딩에 실패해도 실패 상태가 사용자와 운영자에게 분명하게 드러나지 않는다.
- 로그 출력 정책이 분리되어 있지 않아 정상 로그, 디버그 로그, 오류 로그의 목적이 섞인다.
- 사용자 입력 원문이 로그에 과도하게 남을 수 있어 개인정보와 민감정보 노출 위험이 있다.
- 단일 실행 흐름과 조건 분기 중심 처리로 인해 실패 지점과 로그 책임을 추적하기 어렵다.

Phase 4는 기능 확장보다 운영 안정성 확보를 우선한다. 대상 범위는 서버 시작 실패 감지, 로그 정책 명확화, 사용자 입력 원문 출력 관리이다.

### 1.2.1 레거시 코드의 진짜 문제점

현재 코드의 표면적인 문제는 단일 `main` 중심 구조와 긴 `if-else` 흐름이다. 그러나 Phase 4 관점에서 더 중요한 근본 문제는 운영 가능한 시스템으로서의 실패 계약, 로그 계약, 책임 경계가 정의되어 있지 않다는 점이다.

#### 핵심 문제

1. 서버 실행 성공 여부를 신뢰할 수 없다.

   서버가 실제로 시작되지 않아도 운영자가 즉시 실패를 알기 어렵다. 포트 충돌, 바인딩 실패, 초기화 실패가 명확한 상태값과 로그로 표현되지 않는다. 결과적으로 프로그램 실행과 서비스 가능 상태가 구분되지 않는다.

2. 로그가 운영 관찰 도구가 아니라 임시 출력 수단에 가깝다.

   정상 흐름, 사용자 조치 필요 상황, 시스템 실패 상황이 로그 레벨로 일관되게 구분되지 않는다. 장애가 발생했을 때 어떤 로그를 기준으로 판단해야 하는지 불명확하다.

3. 사용자 입력 원문이 로그에 노출될 수 있다.

   고객 피드백에는 개인정보, 주문 정보, 불만 내용, 민감한 표현이 포함될 수 있다. 현재 구조에서는 입력 원문이 디버깅 목적으로 쉽게 출력될 수 있고, 이를 제한하는 정책이 없다.

4. 요청 처리와 운영 책임이 섞여 있다.

   서버 시작, 요청 처리, 분석, 필터링, 화면 응답, 로그 출력이 하나의 흐름에 섞여 있다. 운영 실패를 고치려면 비즈니스 로직까지 함께 이해해야 하며, 작은 운영 안정성 수정도 기존 기능 회귀로 이어질 수 있다.

5. 실패 상황이 요구사항으로 고정되어 있지 않다.

   정상 동작은 어느 정도 구현되어 있지만, 실패 시 어떤 상태가 되어야 하는지는 명확하지 않다. 포트가 이미 사용 중일 때, 로그에 원문이 남을 때, 오류가 발생했을 때의 기대 결과가 테스트 가능한 요구사항으로 정의되어 있지 않다.

#### Phase 4의 본질

Phase 4는 기능 추가 단계가 아니라 운영 신뢰성 복구 단계다.

따라서 Phase 4에서 해결해야 할 핵심 질문은 다음과 같다.

- 서버가 실제로 서비스 가능한 상태인지 판별할 수 있는가?
- 실패했을 때 실패 원인을 1분 이내에 찾을 수 있는가?
- 로그가 사용자 입력 원문을 불필요하게 저장하지 않는가?
- 정상, 경고, 오류 상황이 테스트로 구분되는가?
- 운영 안정성 개선이 기존 피드백 분석 기능을 깨뜨리지 않는가?

### 1.3 목표

1. 서버 포트 바인딩 실패 시 실행 결과가 실패로 종료되어야 한다.
2. 포트 바인딩 실패 시 운영자가 원인을 식별할 수 있는 오류 로그가 1건 이상 남아야 한다.
3. 정상 시작 시 기존 기본 화면 접근 시나리오가 100% 유지되어야 한다.
4. 사용자 피드백 원문이 정보 로그 또는 디버그 로그에 무제한 출력되지 않아야 한다.
5. 정상, 경고, 오류 로그가 각각 구분 가능한 로그 레벨로 기록되어야 한다.

### 1.4 비목표

1. 감정 분석 알고리즘 변경은 Phase 4 범위에 포함하지 않는다.
2. CSV 파싱 및 다운로드 형식 개선은 Phase 4 범위에 포함하지 않는다.
3. UI 화면 구조 개편은 Phase 4 범위에 포함하지 않는다.

## 2. 사용자 및 이해관계자

### 2.1 타깃 사용자

운영 담당 개발자

- 역할: Feedback Analyzer를 로컬 또는 사내 서버에서 실행하고 장애 원인을 확인한다.
- 목표: 서버 실행 실패, 로그 이상, 사용자 입력 노출 문제를 빠르게 식별한다.
- 고충: 서버가 실제로 실행되지 않았는데 성공처럼 보이거나, 로그가 과도해 원인 파악 시간이 길어진다.

### 2.2 주요 시나리오

#### 시나리오 1. 정상 서버 시작 확인

운영 담당 개발자는 애플리케이션을 실행한 뒤 브라우저에서 기본 화면에 접근한다.

성공 기준:

- 서버가 지정 포트에서 정상 시작된다.
- 기본 화면이 표시된다.
- 오류 로그가 생성되지 않는다.

#### 시나리오 2. 포트 충돌 상황 확인

운영 담당 개발자는 동일 포트가 이미 사용 중인 상태에서 애플리케이션을 실행한다.

성공 기준:

- 서버 시작 실패가 감지된다.
- 프로세스가 실패 상태로 종료된다.
- 포트 바인딩 실패 원인을 포함한 오류 로그가 남는다.

#### 시나리오 3. 피드백 입력 후 로그 확인

운영 담당 개발자는 여러 피드백을 입력한 뒤 로그를 확인한다.

성공 기준:

- 정상 흐름 로그는 처리 건수와 상태 중심으로 기록된다.
- 사용자 입력 원문 전체가 반복적으로 출력되지 않는다.
- 오류, 경고, 정보 로그가 구분된다.

## 3. 기능 요구사항

### 3.1 Phase 4 Epic

운영 담당자로서 서버 시작 실패와 로그 노출 위험을 빠르게 식별하고 통제할 수 있어야 한다. 그래야 운영 환경에서 장애 원인 파악 시간을 줄이고 사용자 입력 데이터 노출을 방지할 수 있다.

### 3.2 Story 1. 서버 시작 실패 감지

운영 담당자로서 포트 바인딩 실패를 실행 즉시 알 수 있어야 한다. 그래야 서비스가 정상 실행 중이라고 오해하지 않는다.

#### 인수 조건

- 이미 사용 중인 포트로 서버를 시작하면 실패 상태가 반환되어야 한다.
- 실패 시 오류 로그가 기록되어야 한다.
- 정상 포트에서 서버를 시작하면 기본 화면 접근 테스트가 통과해야 한다.

#### Gherkin

```gherkin
Feature: 서버 시작 실패 감지

Scenario: 이미 사용 중인 포트에서 서버 시작
  Given 동일 포트를 사용하는 프로세스가 이미 실행 중이다
  When Feedback Analyzer 서버를 시작한다
  Then 서버 시작은 실패 상태로 종료된다
  And 포트 바인딩 실패 로그가 기록된다

Scenario: 사용 가능한 포트에서 서버 시작
  Given 지정 포트가 사용 가능하다
  When Feedback Analyzer 서버를 시작한다
  Then 서버는 정상 상태로 실행된다
  And 기본 화면에 접근할 수 있다
```

### 3.3 Story 2. 로그 레벨 정책 정리

운영 담당자로서 정상, 경고, 오류 로그를 구분해서 확인할 수 있어야 한다. 그래야 장애 원인을 로그 레벨 기준으로 빠르게 필터링할 수 있다.

#### 인수 조건

- 정상 처리 흐름은 정보 로그로 기록되어야 한다.
- 필터 결과 없음, 입력 없음 같은 사용자 조치 가능 상황은 경고 로그로 기록되어야 한다.
- 서버 시작 실패와 처리 예외는 오류 로그로 기록되어야 한다.
- 디버그 로그는 설정된 조건에서만 출력되어야 한다.

#### Gherkin

```gherkin
Feature: 로그 레벨 정책

Scenario: 정상 처리 로그 기록
  Given 서버가 정상 실행 중이다
  When 사용자가 유효한 피드백을 입력한다
  Then 정보 로그가 기록된다
  And 오류 로그는 기록되지 않는다

Scenario: 사용자 조치 가능 상황 로그 기록
  Given 분석 대상 피드백이 없다
  When 사용자가 필터를 실행한다
  Then 경고 로그가 기록된다

Scenario: 서버 시작 실패 로그 기록
  Given 지정 포트가 이미 사용 중이다
  When 서버를 시작한다
  Then 오류 로그가 기록된다
```

### 3.4 Story 3. 사용자 입력 원문 로그 출력 제한

운영 담당자로서 사용자 입력 원문이 로그에 과도하게 남지 않도록 통제할 수 있어야 한다. 그래야 개인정보와 민감정보 노출 위험을 줄일 수 있다.

#### 인수 조건

- 여러 피드백 입력 시 사용자 입력 원문 전체가 반복 출력되지 않아야 한다.
- 처리 건수, 성공 여부, 실패 사유는 로그로 확인 가능해야 한다.
- 오류 원인 파악에 필요한 메타데이터는 남아야 한다.
- 사용자 입력 원문을 남겨야 하는 경우에는 디버그 정책에 의해 통제되어야 한다.

#### Gherkin

```gherkin
Feature: 사용자 입력 로그 보호

Scenario: 여러 피드백 입력 후 로그 확인
  Given 사용자가 여러 피드백을 입력한다
  When 로그를 확인한다
  Then 사용자 입력 원문 전체가 반복 출력되지 않는다
  And 처리된 피드백 개수는 확인할 수 있다

Scenario: 오류 발생 시 로그 확인
  Given 처리 중 오류가 발생한다
  When 로그를 확인한다
  Then 오류 유형과 실패 위치를 식별할 수 있다
  And 사용자 입력 원문 전체는 출력되지 않는다
```

### 3.5 운영 실패 계약 정의

시스템은 서버 시작 결과를 성공 또는 실패로 명확히 구분해야 한다.

#### 요구사항

- 서버 시작 성공 시 서비스 접근 가능 상태를 보장해야 한다.
- 서버 시작 실패 시 실패 상태로 종료해야 한다.
- 포트 바인딩 실패는 별도 실패 원인으로 식별되어야 한다.
- 알 수 없는 서버 시작 실패는 추적 가능한 실패 이벤트로 기록되어야 한다.

#### 인수 조건

- 사용 중인 포트로 서버를 시작하면 실패 상태가 반환된다.
- 실패 로그에는 실패 원인이 포함된다.
- 정상 포트에서 서버를 시작하면 기존 기본 화면 Golden Master Test가 통과한다.

### 3.6 로그 출력 계약 정의

시스템은 로그를 임시 출력이 아닌 운영 관찰 수단으로 사용해야 한다.

#### 요구사항

- 정상 처리 흐름은 INFO로 기록한다.
- 사용자 조치가 필요한 상황은 WARNING으로 기록한다.
- 시스템 실패와 예외는 ERROR로 기록한다.
- 개발 디버깅 정보는 DEBUG로 기록하며 기본 운영 로그와 분리한다.
- 사용자 입력 원문 전체는 기본 로그에 기록하지 않는다.

#### 인수 조건

- 정상 피드백 입력 시 INFO 로그가 남는다.
- 필터 결과 없음 또는 입력 없음 상황은 WARNING 로그로 남는다.
- 서버 시작 실패는 ERROR 로그로 남는다.
- 여러 피드백 입력 후에도 사용자 입력 원문 전체가 반복 출력되지 않는다.

## 4. 비기능 요구사항

### 4.1 기술 스택

- 언어: C++17 이상
- 빌드 시스템: CMake
- 테스트 프레임워크: Catch2
- 실행 환경: 로컬 또는 서버 프로세스 기반 웹 애플리케이션

### 4.2 아키텍처 원칙

#### SRP

- 서버 시작 책임, 로그 기록 책임, 요청 처리 책임은 서로 다른 변경 이유를 가져야 한다.
- 로그 정책 변경이 피드백 분석 결과를 변경하면 안 된다.
- 서버 시작 실패 처리 변경이 UI 렌더링을 변경하면 안 된다.

#### OCP

- 신규 로그 레벨 또는 신규 운영 이벤트 추가 시 기존 분석 로직을 수정하지 않아야 한다.
- 신규 입력 유형 추가 시 서버 시작 실패 처리 로직을 수정하지 않아야 한다.
- 신규 검증 규칙 추가 시 기존 정상 시작 시나리오가 변경되지 않아야 한다.

#### BCE 레이어

- Boundary: HTTP 요청, 응답, 화면 출력, 파일 입출력, 서버 시작 및 외부 입출력 접점
- Control: 사용자 요청 흐름, 운영 이벤트 흐름, 오류 처리 흐름 조정
- Entity: 피드백 데이터, 분석 기준, 운영 이벤트 판단에 필요한 순수 규칙

#### 의존성 방향

- Boundary는 Control을 호출한다.
- Control은 Entity를 사용한다.
- Entity는 Control과 Boundary를 참조하지 않는다.
- 로그 정책은 분석 규칙을 참조하지 않는다.
- 분석 규칙은 로그 출력 구현을 참조하지 않는다.

### 4.3 테스트 커버리지 목표

- Domain 테스트 커버리지: 라인 85% 이상, 브랜치 80% 이상
- Boundary 테스트 커버리지: 라인 70% 이상, 브랜치 60% 이상
- Data 테스트 커버리지: 라인 80% 이상, 브랜치 70% 이상

Phase 4 필수 테스트:

- 정상 서버 시작 테스트 1개 이상
- 포트 바인딩 실패 테스트 1개 이상
- 로그 레벨 분리 테스트 3개 이상
- 사용자 입력 원문 로그 제한 테스트 1개 이상
- 기존 기본 화면 Golden Master 테스트 1개 이상

### 4.4 확장성 원칙

- 신규 운영 이벤트 추가 시 기존 이벤트 판단 테스트는 100% 통과해야 한다.
- 신규 로그 레벨 추가 시 기존 로그 레벨 이름과 의미는 변경하지 않는다.
- 새 단위 추가 시 기존 Domain 로직 파일 변경 수는 1개 이하로 제한한다.
- 새 단위 추가 시 기존 Boundary 테스트 실패 건수는 0건이어야 한다.
- 새 단위 추가 시 기존 public 동작 변경이 발생하면 변경 사유와 RED 테스트를 먼저 작성한다.

### 4.5 운영 관찰성 요구사항

Phase 4 완료 후 운영자는 로그만 보고 다음 정보를 확인할 수 있어야 한다.

- 서버 시작 성공 여부
- 서버 시작 실패 원인
- 사용자 요청 처리 성공 여부
- 사용자 조치 필요 상황
- 시스템 예외 발생 여부
- 처리된 피드백 건수

로그만으로 확인하지 않아도 되는 정보는 다음과 같다.

- 사용자 피드백 원문 전체
- 업로드 파일 전체 내용
- 분석 대상 텍스트 전문
- 개인정보로 해석될 수 있는 자유 입력값

### 4.6 실패 상태 요구사항

시스템 실패 상태는 다음 기준을 만족해야 한다.

- 실패는 조용히 무시되지 않는다.
- 실패는 성공 메시지로 표시되지 않는다.
- 실패는 로그 레벨 ERROR로 기록된다.
- 실패 원인은 운영자가 재현 가능한 수준으로 표현된다.
- 실패 후 프로세스 상태는 테스트로 검증 가능해야 한다.

## 5. 데이터 요구사항

### 5.1 로그 데이터

로그는 다음 필드를 포함해야 한다.

- timestamp: 로그 발생 시각
- level: INFO, WARNING, ERROR, DEBUG 중 하나
- event: 서버 시작, 서버 시작 실패, 피드백 입력, 필터 실행, 예외 발생 중 하나
- message: 운영자가 읽을 수 있는 한국어 또는 영어 메시지
- count: 처리 건수가 있는 경우 0 이상의 정수
- error_reason: 실패 상황에서 원인 문자열
- request_scope: 요청 단위 추적이 가능한 식별자

### 5.2 사용자 입력 데이터 보호

사용자 입력 원문은 기본 정보 로그에 저장하지 않는다.

허용되는 데이터:

- 입력 건수
- 처리 성공 여부
- 검증 실패 사유
- 필터 결과 건수
- 오류 유형

제한되는 데이터:

- 피드백 원문 전체
- 업로드 파일의 전체 내용
- 사용자가 입력한 자유 텍스트 전체
- 개인정보로 해석될 수 있는 문자열

### 5.3 서버 상태 데이터

서버 시작 결과는 다음 상태 중 하나로 표현되어야 한다.

- STARTED
- BIND_FAILED
- CONFIG_INVALID
- UNKNOWN_ERROR

각 상태는 운영 로그에서 구분 가능해야 한다.

## 6. 출력 요구사항

### 6.1 정상 시작 출력

서버 정상 시작 시 출력은 다음 조건을 만족해야 한다.

- 접속 가능한 주소가 표시된다.
- 오류 메시지는 표시되지 않는다.
- 기본 화면 접근 테스트가 통과한다.

### 6.2 서버 시작 실패 출력

서버 시작 실패 시 출력은 다음 조건을 만족해야 한다.

- 실패 상태로 종료된다.
- 포트 바인딩 실패 여부가 로그에 남는다.
- 운영자가 다음 조치를 판단할 수 있는 원인이 표시된다.

### 6.3 로그 출력

로그 출력은 다음 조건을 만족해야 한다.

- 정상 처리 로그는 INFO로 구분된다.
- 사용자 조치 가능 상황은 WARNING으로 구분된다.
- 시스템 실패와 예외는 ERROR로 구분된다.
- DEBUG 로그는 설정 조건을 만족할 때만 출력된다.
- 사용자 입력 원문 전체는 기본 로그에 남지 않는다.

## 8. 용어 정의

### Boundary

외부 시스템, 사용자, HTTP 요청, 파일, 콘솔 출력과 맞닿는 계층이다.

### Control

사용자 요청과 시스템 동작 흐름을 조정하는 계층이다.

### Entity

피드백, 분석 기준, 운영 상태 판단 규칙 같은 핵심 도메인 데이터를 표현하는 계층이다.

### Golden Master Test

현재 정상으로 인정되는 사용자 흐름을 리팩토링 후에도 보존하기 위한 회귀 테스트이다.

### RED CASE

현재 코드에서 버그 또는 구조적 한계로 실패가 예상되는 테스트이다. 관련 수정이 완료되면 Green으로 전환되어야 한다.

### Green

테스트가 기대 결과를 만족해 통과한 상태이다.

### Phase 4

운영 안정성을 대상으로 하는 리팩토링 단계이다. 범위는 서버 시작 실패 감지, 로그 정책 명확화, 사용자 입력 원문 출력 관리이다.

### 포트 바인딩 실패

서버가 지정된 네트워크 포트를 사용할 수 없어 시작하지 못하는 상태이다.

### 로그 레벨

로그의 심각도와 목적을 구분하는 값이다. Phase 4에서는 INFO, WARNING, ERROR, DEBUG를 사용한다.

### 사용자 입력 원문

사용자가 직접 입력한 피드백 텍스트 또는 업로드 파일에 포함된 자유 텍스트 전체를 의미한다.

### 운영 실패 계약

서버 시작, 요청 처리, 로그 기록 중 실패가 발생했을 때 시스템이 어떤 상태를 반환하고 어떤 로그를 남길지 정의한 요구사항이다.

### 로그 출력 계약

INFO, WARNING, ERROR, DEBUG 로그가 각각 어떤 상황에서 기록되어야 하는지 정의한 규칙이다.

### 운영 신뢰성

시스템이 정상 상태와 실패 상태를 명확히 구분하고, 운영자가 실패 원인을 빠르게 확인할 수 있는 품질 속성이다.

### 원문 로그 노출

사용자가 입력한 자유 텍스트 전체가 운영 로그 또는 디버그 로그에 그대로 남는 상태를 의미한다.
