# Regacy Code 분석 리포트

## 1. 목적

이 문서는 현재 Feedback Analyzer C++ 코드에서 발견된 레거시 코드 문제와 구조적 위험을 정리한 분석 리포트이다. 개발자가 이후 수정 방향을 잡을 때 어떤 영역을 우선적으로 개선해야 하는지 이해할 수 있도록, 문제의 원인과 영향 그리고 권장 개선 방향을 함께 정리한다.

## 2. 종합 진단

현재 코드는 단일 사용자와 정상 입력을 전제로 하면 기본 기능은 동작할 수 있다. 그러나 웹 애플리케이션으로 운영되거나 여러 사용자가 동시에 접근하는 상황에서는 데이터 섞임, 잘못된 분석 결과, 이전 필터 결과 다운로드, CSV 처리 오류 같은 문제가 발생할 가능성이 높다.

가장 큰 문제는 개별 함수의 버그보다 전체 구조의 결합도에 있다. HTTP 요청 처리, 화면 렌더링, CSV 파싱, 분석, 필터링, 다운로드, 상태 관리가 강하게 묶여 있어 기능을 수정할 때 영향 범위를 예측하기 어렵다. 또한 전역 또는 정적 상태에 의존하는 부분이 많아 테스트와 동시성 대응이 어렵다.

## 3. 주요 문제 요약

| 구분 | 문제 | 주요 위험 |
| --- | --- | --- |
| 상태 관리 | 사용자별 세션이 아닌 전역 공유 상태 사용 | 사용자 간 데이터 섞임, 동시 요청 충돌 |
| 구조 | 요청 처리, UI 렌더링, 분석 로직이 한 흐름에 집중 | 수정 시 회귀 위험 증가 |
| 분석 기준 | 분석 기준과 필터 기준이 서로 다름 | 화면 결과와 필터 결과 불일치 |
| CSV 처리 | 단순 파싱과 미흡한 이스케이프 처리 | 데이터 유실, 깨진 CSV, 잘못된 분석 |
| 다운로드 | 마지막 필터 결과에 의존 | 이전 결과 다운로드, 빈 결과 다운로드 |
| 테스트성 | 자동 테스트 구조 부족 | 수정 후 안정성 검증 어려움 |
| 유지보수성 | 중복 로직과 사용되지 않는 구성 요소 존재 | 버그 원인 추적 어려움 |

## 4. Legacy Code에서 발견된 문제

### 4.1 책임이 과도하게 집중된 구조

현재 서버 요청 처리, HTML 생성, 폼 파싱, CSV 파싱, 분석 호출, 필터링, 다운로드 응답 생성이 하나의 실행 흐름에 집중되어 있다. 이 구조에서는 작은 기능 변경도 여러 책임을 동시에 건드리게 된다.

이로 인해 다음과 같은 문제가 발생한다.

- 화면 변경이 분석 로직에 영향을 줄 수 있다.
- CSV 처리 변경이 업로드 흐름 전체에 영향을 줄 수 있다.
- 필터링 결과 표시 방식 변경이 다운로드 결과에도 영향을 줄 수 있다.
- 기능별 단위 테스트가 어렵다.

수정 방향은 기능별 책임을 분리하는 것이다. 요청 처리, 상태 관리, 분석, 필터링, CSV 입출력, 화면 렌더링의 역할을 명확히 나누어야 한다.

### 4.2 전역 상태와 정적 상태 의존

피드백 목록, 필터 결과, 분석 결과 등이 전역 또는 정적 상태에 저장된다. 이 방식은 단순한 콘솔 프로그램에서는 문제가 적을 수 있지만, 웹 서버에서는 여러 요청이 동시에 들어오기 때문에 위험하다.

예상 가능한 문제는 다음과 같다.

- 사용자 A의 입력이 사용자 B의 화면에 반영될 수 있다.
- 사용자 A가 필터링한 결과를 사용자 B가 다운로드할 수 있다.
- 입력, 필터, 다운로드 요청이 동시에 실행되면 데이터가 손상될 수 있다.
- 테스트 실행 시 이전 테스트의 상태가 다음 테스트에 영향을 줄 수 있다.

수정 방향은 요청 또는 사용자 단위로 상태 범위를 명확히 하는 것이다. 최소한 공유 상태에 대한 접근 정책을 정하고, 동시 접근에 대한 보호 장치가 필요하다.

### 4.3 분석 기준과 필터 기준의 불일치

감정 분석에서 사용하는 키워드 기준과 감정 필터에서 사용하는 키워드 기준이 별도로 존재한다. 따라서 같은 피드백이 분석 결과에서는 긍정으로 집계되지만, 필터링에서는 다른 감정으로 분류될 수 있다.

카테고리 기준도 유사한 위험이 있다. 분석에서는 대표 키워드 중심으로 집계하고, 필터에서는 하위 키워드 중심으로 판단하는 구조라서 분석 결과와 필터 결과가 다르게 보일 수 있다.

수정 방향은 분석과 필터가 같은 기준 데이터를 사용하도록 정리하는 것이다. 하나의 기준에서 감정과 카테고리를 판단하고, 화면 표시와 필터링이 동일한 판단 결과를 사용해야 한다.

### 4.4 CSV 입력 처리의 취약성

CSV 업로드는 첫 줄을 무조건 헤더로 간주하고 첫 번째 컬럼만 사용한다. 문서에서는 특정 텍스트 컬럼을 요구하지만, 실제 동작은 컬럼 이름을 검증하지 않는다. 컬럼 순서가 바뀌면 잘못된 데이터를 분석할 수 있고, 헤더가 없는 파일에서는 첫 번째 데이터가 유실된다.

또한 쉼표, 따옴표, 줄바꿈이 포함된 일반적인 CSV 데이터를 안정적으로 처리하기 어렵다. 실제 고객 피드백에는 쉼표나 줄바꿈이 자주 포함될 수 있으므로 데이터 품질 문제가 쉽게 발생한다.

수정 방향은 CSV 입력 형식을 명확히 검증하고, 컬럼 이름과 인코딩, 빈 값, 특수문자 처리를 일관되게 다루는 것이다.

### 4.5 CSV 다운로드 처리의 위험

다운로드 결과는 필터링 결과 상태에 의존한다. 필터링을 수행하지 않은 상태에서는 결과가 비어 있을 수 있고, 필터링 결과가 없는 경우 이전 결과가 남아 잘못된 파일이 내려갈 수 있다.

또한 다운로드 CSV 생성 시 피드백 텍스트 안의 쉼표, 따옴표, 줄바꿈을 안전하게 처리하지 않으면 파일이 깨질 수 있다.

수정 방향은 다운로드할 데이터의 기준을 명확히 정하고, 필터 결과가 없는 경우에도 이전 상태가 재사용되지 않도록 해야 한다. CSV 출력은 CSV 규칙에 맞게 이스케이프되어야 한다.

### 4.6 입력값 검증과 오류 처리 부족

빈 입력, 공백 입력, 잘못된 폼 데이터, 파일 없음, 빈 파일, 잘못된 CSV 형식 등에 대한 사용자 피드백이 충분하지 않다. 일부 오류는 조용히 무시되며, 사용자는 성공한 것처럼 오해할 수 있다.

수정 방향은 입력 단계에서 유효성을 검증하고, 실패 사유를 명확히 사용자에게 전달하는 것이다. 개발자 로그와 사용자 메시지도 구분되어야 한다.

### 4.7 동시성 안전성 부족

웹 서버는 여러 요청을 동시에 처리할 수 있다. 하지만 현재 공유 데이터 접근에는 동기화가 보이지 않는다. 특히 입력, 업로드, 필터링, 다운로드가 같은 데이터에 접근하기 때문에 데이터 경합 가능성이 있다.

위험 사례는 다음과 같다.

- 업로드 중 다른 사용자가 필터링을 실행하는 경우
- 필터링 중 다운로드가 실행되는 경우
- 입력 추가 중 분석 결과를 계산하는 경우
- 동시에 여러 사용자가 피드백을 추가하는 경우

수정 방향은 공유 상태를 줄이고, 불가피한 공유 상태에는 동시 접근 정책을 적용하는 것이다.

### 4.8 사용되지 않거나 역할이 모호한 코드

파일 처리처럼 보이는 구성 요소가 실제 파일 저장 또는 다운로드 흐름에 사용되지 않는다. 세션 관련 구성 요소도 이름과 실제 동작이 다르게 보인다. 이런 코드는 유지보수자가 잘못된 위치를 수정하게 만들 수 있다.

수정 방향은 실제 사용되지 않는 코드를 정리하고, 이름과 책임을 실제 동작에 맞게 맞추는 것이다.

## 5. 추가 버그 위험 분석

### 5.1 이전 결과 재사용 버그

필터 결과가 없을 때 결과 저장소가 초기화되지 않으면 이전 필터 결과가 그대로 남을 수 있다. 이 경우 사용자는 현재 조건의 결과가 아니라 과거 조건의 결과를 다운로드하게 된다.

### 5.2 사용자 데이터 혼합 버그

전역 상태를 통해 피드백 목록을 관리하면 사용자별 데이터 경계가 없다. 한 사용자가 입력한 데이터가 다른 사용자의 분석 결과나 다운로드 결과에 섞일 수 있다.

### 5.3 오분류 버그

단순 문자열 포함 여부만으로 감정과 카테고리를 판단하므로 다음과 같은 표현에서 오분류가 발생할 수 있다.

- 긍정 단어와 부정 단어가 함께 있는 문장
- 부정 표현이 포함된 문장
- 단어 일부가 우연히 포함된 문장
- 중립 표현과 긍정 또는 부정 표현이 함께 있는 문장

### 5.4 CSV 데이터 유실 버그

헤더가 없는 CSV를 업로드하면 첫 번째 데이터가 사라질 수 있다. 또한 텍스트 컬럼이 첫 번째가 아닌 경우 다른 컬럼 값이 피드백으로 들어갈 수 있다.

### 5.5 깨진 CSV 다운로드 버그

피드백에 쉼표, 따옴표, 줄바꿈이 포함된 경우 다운로드 파일의 행과 컬럼 구조가 깨질 수 있다. 이후 엑셀이나 다른 분석 도구에서 열 때 잘못된 데이터로 해석될 수 있다.

### 5.6 서버 시작 실패 감지 누락

서버가 포트를 열지 못하거나 시작에 실패해도 이를 명확히 처리하지 않으면 운영자는 서비스가 정상 실행된 것으로 오해할 수 있다.

## 6. 구조적 위험

### 6.1 변경 영향 범위가 넓다

기능별 경계가 명확하지 않아 한 기능을 수정할 때 다른 기능이 함께 영향을 받을 가능성이 높다. 이는 버그 수정 속도를 늦추고 회귀 버그를 증가시킨다.

### 6.2 테스트 도입이 어렵다

핵심 로직이 HTTP 요청 처리와 전역 상태에 묶여 있다. 따라서 감정 분석, 카테고리 분석, CSV 파싱, 필터링을 독립적으로 검증하기 어렵다.

### 6.3 데이터 기준 관리가 어렵다

감정 키워드, 카테고리 키워드, 화면 카테고리 목록이 여러 위치에 나뉘어 있다. 새로운 카테고리를 추가하거나 키워드를 수정할 때 일부만 변경되면 결과 불일치가 발생한다.

### 6.4 운영 환경에서 문제가 커질 수 있다

로컬 단일 사용자 테스트에서는 문제가 드러나지 않을 수 있다. 하지만 실제 운영 환경에서는 동시 요청, 잘못된 CSV, 반복 다운로드, 다중 사용자 사용으로 인해 문제가 빠르게 드러날 수 있다.

## 7. 수정 우선순위 제안

### 1순위: 데이터 섞임과 다운로드 오류 방지

가장 먼저 사용자 데이터와 필터 결과의 범위를 명확히 해야 한다. 이전 필터 결과가 재사용되지 않도록 하고, 다운로드 대상 데이터가 현재 요청의 결과인지 명확히 보장해야 한다.

### 2순위: 분석 기준과 필터 기준 통합

감정 분석과 감정 필터가 동일한 판단 기준을 사용하도록 정리해야 한다. 카테고리 분석과 카테고리 필터도 같은 기준을 공유해야 한다.

### 3순위: CSV 입출력 안정화

CSV 입력에서는 헤더, 컬럼명, 빈 값, 특수문자, 인코딩을 검증해야 한다. CSV 출력에서는 쉼표, 따옴표, 줄바꿈을 안전하게 처리해야 한다.

### 4순위: 책임 분리

요청 처리, 렌더링, 분석, 필터링, CSV 처리, 상태 관리를 분리해야 한다. 이 작업은 단번에 크게 바꾸기보다 위험도가 높은 흐름부터 단계적으로 진행하는 것이 좋다.

### 5순위: 테스트 기반 마련

감정 분석, 카테고리 분석, 필터링, CSV 파싱, 다운로드 데이터 생성 같은 핵심 로직부터 테스트할 수 있도록 구조를 정리해야 한다.

## 8. 권장 개선 방향

### 상태 관리

- 사용자별 데이터와 전체 공유 데이터를 구분한다.
- 필터 결과를 전역으로 보관하는 방식을 줄인다.
- 요청 간 공유되는 데이터에는 동시성 정책을 적용한다.
- 함수 이름과 실제 동작이 일치하도록 정리한다.

### 분석과 필터링

- 감정 판단 기준을 하나로 통합한다.
- 카테고리 판단 기준을 하나로 통합한다.
- 분석 결과와 필터 결과가 같은 판단 결과를 기반으로 동작하도록 한다.
- 중복 키워드를 제거하고 기준 데이터의 소유 위치를 명확히 한다.

### CSV 처리

- 입력 CSV의 헤더와 필수 컬럼을 검증한다.
- 컬럼 순서가 바뀌어도 올바른 텍스트 컬럼을 읽도록 한다.
- 쉼표, 따옴표, 줄바꿈이 포함된 텍스트를 안전하게 처리한다.
- 다운로드 CSV도 표준 규칙에 맞게 생성한다.

### 오류 처리와 사용자 피드백

- 빈 입력, 빈 파일, 잘못된 CSV, 파일 누락을 명확히 구분한다.
- 사용자에게 성공과 실패를 정확히 알려준다.
- 운영 로그와 사용자 메시지를 분리한다.
- 서버 시작 실패를 감지하고 명확히 보고한다.

- 카테고리 필터 결과 검증

## 9. 결론

현재 코드의 핵심 위험은 전역 상태, 책임 집중, 기준 데이터 불일치, CSV 처리 취약성이다. 이 문제들은 서로 연결되어 있어 단순히 한두 개의 조건문을 추가하는 방식으로는 안정적으로 해결하기 어렵다.

수정은 먼저 사용자 데이터 섞임과 잘못된 다운로드를 막는 것부터 시작하는 것이 좋다. 이후 분석 기준과 필터 기준을 통합하고, CSV 입출력을 안정화한 다음, 기능별 책임 분리와 테스트 도입으로 확장하는 순서가 적절하다.

이 방향으로 개선하면 현재 기능을 유지하면서도 다중 사용자 환경, 실제 CSV 데이터, 반복적인 기능 변경에 더 안전한 구조로 발전시킬 수 있다.
