# Golden Master 회귀테스트 계획

## 1. 목적

이 문서는 Feedback Analyzer의 다음 리팩토링 단계에서 기존 Green 동작을 보존하기 위한 Golden Master 회귀테스트 계획이다.

참조 문서:

- `README.md`
- `docs/Regacy_Code_리팩토링_테스트_계획.md`
- `docs/red_stage_development_report.md`
- `docs/Regacy_Code_분석_리포트.md`

테스트 계획의 목적은 다음과 같다.

- RED 단계에서 Green으로 전환된 동작을 리팩토링 중 회귀 없이 유지한다.
- 전역 상태, CSV 처리, 분석/필터 기준, 다운로드, 입력 검증, 로깅 정책의 회귀를 조기에 발견한다.
- C++17, CMake, Catch2 기반으로 반복 실행 가능한 자동 테스트 묶음을 만든다.
- 리팩토링 커밋마다 기능 변경 여부를 빠르게 판정할 수 있는 기준선을 제공한다.

## 2. 작업 제약

- 이 문서는 테스트 계획 문서만 생성한다.
- 현재 단계에서는 프로덕션 코드와 테스트 코드를 변경하지 않는다.
- 실제 테스트 구현은 이후 별도 커밋에서 진행한다.
- 테스트 구현 시에도 Golden Master는 알려진 버그를 정답으로 고정하지 않고, RED 단계 완료 후 확정된 Green 동작을 기준으로 삼는다.

## 3. 테스트 환경 제안

### 3.1 기술 스택

- Language: C++17
- Build: CMake
- Test Framework: Catch2
- Target 예시:
  - `feedback_analyzer_golden_master_tests`
  - `feedback_analyzer_unit_regression_tests`

### 3.2 CMake 구성 방향

이 계획은 코드 변경을 수행하지 않지만, 이후 구현 시 다음 구조를 권장한다.

```text
tests/
  golden_master/
    golden_master_http_flow_test.cpp
    golden_master_csv_flow_test.cpp
    golden_master_analysis_filter_test.cpp
    golden_master_logging_test.cpp
```

권장 원칙:

- 테스트 타깃은 `CMAKE_CXX_STANDARD 17`을 사용한다.
- Catch2는 `find_package(Catch2 CONFIG QUIET)` 또는 FetchContent 방식 중 프로젝트 정책에 맞춰 선택한다.
- HTTP 포트를 실제로 열지 않는 테스트는 fake `httplib` 경계로 route handler를 직접 호출한다.
- 실제 서버 시작/포트 충돌 검증은 별도 느린 통합 테스트 그룹으로 분리한다.
- 각 테스트는 독립 fixture를 사용하고, 실행 전후로 세션/필터 상태를 초기화한다.

## 4. Golden Master 데이터셋

### 4.1 기본 피드백

| 이름 | 텍스트 | 기대 기준 |
| --- | --- | --- |
| positive_shipping | 배송이 빠르고 서비스가 좋아요 | 긍정, 배송/서비스 |
| negative_shipping | 배송지연 때문에 너무 불편하고 실망했습니다 | 부정, 배송/사용성 |
| price_value | 가격이 저렴하고 가성비가 좋아요 | 긍정, 가격 |
| quality_good | 제품 품질이 좋고 마감이 훌륭합니다 | 긍정, 품질 |
| service_kind | 상담 응대가 친절해서 만족합니다 | 긍정, 서비스 |
| usability_bad | 사용법이 어렵고 설명서가 불편합니다 | 부정, 사용성 |
| neutral_received | 제품을 오늘 받았습니다 | 중립 또는 키워드 없음 |

### 4.2 CSV 데이터

정상 CSV:

```csv
text
배송이 빠르고 서비스가 좋아요
가격이 저렴하고 가성비가 좋아요
제품 품질이 좋고 마감이 훌륭합니다
```

컬럼 순서 변경 CSV:

```csv
id,text
1,배송이 빠르고 서비스가 좋아요
2,가격이 저렴하고 가성비가 좋아요
```

특수문자 CSV:

```csv
text
"배송은 빠르지만, 포장이 약해요"
"제품에 ""흠집""이 있어요"
"첫 줄
둘째 줄"
```

## 5. 테스트 격리 원칙

- 모든 테스트는 시작 시 세션 피드백 상태와 필터 다운로드 상태를 비운다.
- 테스트 간 데이터 공유를 허용하지 않는다.
- 사용자별 상태 검증은 `Cookie: sid=<id>`를 명시적으로 사용한다.
- 다운로드 검증은 현재 세션의 최신 필터 결과만 대상으로 삼는다.
- 로그 검증은 stdout/stderr 캡처를 사용하되, 사용자 입력 원문이 기본 출력에 남지 않는지만 확인한다.
- 시간 문자열, HTML 전체 문자열처럼 변동 가능성이 큰 값은 snapshot 전체 비교 대신 핵심 selector/text 포함 여부로 검증한다.

## 6. 회귀테스트 케이스

### GM-01. 초기 화면 렌더링

목적:

- 서버 route 등록 후 기본 화면이 정상 렌더링되는지 확인한다.

절차:

1. 테스트 fixture에서 route를 부팅한다.
2. `GET /`을 호출한다.
3. HTML 응답을 검사한다.

기대 결과:

- 응답 content type은 `text/html; charset=UTF-8`이다.
- 피드백 입력 영역, CSV 업로드 영역, 감정 필터, 카테고리 필터가 포함된다.
- 오류 메시지가 기본 표시되지 않는다.

### GM-02. 단일 직접 입력 분석

목적:

- 정상 직접 입력이 피드백 목록에 추가되고 분석 결과로 표시되는지 보존한다.

절차:

1. `POST /analyze`에 `text=배송이 빠르고 서비스가 좋아요`를 전달한다.
2. 응답 HTML과 세션 피드백 상태를 확인한다.

기대 결과:

- 피드백 개수는 1개다.
- 성공 메시지에 `1개의 피드백`이 포함된다.
- 감정 분석 결과에 긍정이 포함된다.

### GM-03. 여러 직접 입력 누적 분석

목적:

- 같은 세션에서 여러 직접 입력이 누적되는 정상 흐름을 보존한다.

절차:

1. 같은 `sid`로 긍정 배송 피드백을 입력한다.
2. 같은 `sid`로 부정 배송 피드백을 입력한다.
3. 같은 `sid`로 가격 피드백을 입력한다.

기대 결과:

- 세션 피드백 개수는 3개다.
- 긍정과 부정 분석 결과가 함께 표시된다.
- 배송과 가격 관련 카테고리 결과가 표시된다.

### GM-04. 사용자 세션 분리

목적:

- RED 단계에서 개선한 사용자별 상태 분리가 유지되는지 확인한다.

절차:

1. `sid=user-a`로 피드백을 입력한다.
2. `sid=user-b`로 필터를 실행한다.

기대 결과:

- user-b 응답에는 `분석할 피드백이 없습니다.`가 포함된다.
- user-a의 피드백 원문이 user-b 화면에 포함되지 않는다.

### GM-05. 정상 CSV 업로드

목적:

- `text` 헤더가 있는 정상 CSV 업로드 흐름을 보존한다.

절차:

1. `text` 컬럼이 있는 CSV를 업로드한다.
2. 세션 피드백 상태와 응답 메시지를 확인한다.

기대 결과:

- 업로드한 행 수만큼 피드백이 추가된다.
- 성공 메시지가 표시된다.
- 오류 또는 경고 메시지가 표시되지 않는다.

### GM-06. CSV text 컬럼 위치 변경

목적:

- `text` 컬럼이 첫 번째가 아니어도 올바른 값을 읽는지 확인한다.

절차:

1. `id,text` 헤더 CSV를 업로드한다.
2. 저장된 피드백 텍스트를 확인한다.

기대 결과:

- `id` 값이 피드백으로 저장되지 않는다.
- `text` 컬럼 값만 피드백으로 저장된다.

### GM-07. 헤더 없는 CSV 데이터 보존

목적:

- 헤더 없는 CSV에서 첫 데이터 행이 조용히 유실되지 않는지 확인한다.

절차:

1. 첫 줄부터 피드백인 CSV를 업로드한다.
2. 저장된 피드백 개수와 첫 번째 피드백을 확인한다.

기대 결과:

- 첫 번째 행이 피드백으로 저장된다.
- 전체 데이터 행 수가 보존된다.

### GM-08. CSV quoted field 파싱

목적:

- 쉼표, 따옴표, 줄바꿈이 포함된 CSV 필드 보존을 확인한다.

절차:

1. 쉼표 포함 피드백 CSV를 업로드한다.
2. escaped quote 포함 피드백 CSV를 업로드한다.
3. quoted newline 포함 피드백 CSV를 업로드한다.

기대 결과:

- 쉼표 포함 텍스트가 하나의 피드백으로 저장된다.
- `""`는 필드 내 `"`로 복원된다.
- quoted newline은 하나의 피드백 텍스트 안에 보존된다.

### GM-09. 감정 필터 정상 동작

목적:

- 감정 분석 기준과 감정 필터 기준의 일관성을 보존한다.

절차:

1. 긍정, 부정, 중립 데이터셋을 입력한다.
2. `sentiment=긍정&keyword=전체` 필터를 실행한다.
3. `sentiment=부정&keyword=전체` 필터를 실행한다.

기대 결과:

- 긍정 필터에는 긍정 데이터만 포함된다.
- 부정 필터에는 부정 데이터만 포함된다.
- 분석 집계와 필터 결과 수가 일관된다.

### GM-10. 카테고리 필터 정상 동작

목적:

- 카테고리 분석 기준과 카테고리 필터 기준의 일관성을 보존한다.

절차:

1. 배송, 품질, 가격, 서비스, 사용성 피드백을 입력한다.
2. 각 카테고리 필터를 실행한다.

기대 결과:

- 선택 카테고리와 관련된 피드백이 포함된다.
- 무관한 카테고리 피드백이 과도하게 섞이지 않는다.
- 화면 선택지와 실제 필터 가능 카테고리가 일치한다.

### GM-11. 필터 결과 다운로드

목적:

- 필터 결과가 있는 경우 다운로드 CSV가 현재 필터 결과만 포함하는지 확인한다.

절차:

1. 여러 피드백을 입력한다.
2. 특정 감정 또는 카테고리 필터를 실행한다.
3. `GET /download`를 호출한다.

기대 결과:

- `Content-Disposition` attachment 헤더가 있다.
- CSV에는 현재 필터 결과에 해당하는 피드백만 포함된다.
- UTF-8 한국어 텍스트가 보존된다.

### GM-12. 필터 전 다운로드 차단

목적:

- 필터 실행 전 다운로드가 의미 없는 attachment로 제공되지 않는지 확인한다.

절차:

1. route를 부팅한다.
2. 필터를 실행하지 않고 `GET /download`를 호출한다.

기대 결과:

- `Content-Disposition` 헤더가 없다.
- 응답 body는 비어 있다.
- 이전 테스트나 이전 세션의 필터 결과가 포함되지 않는다.

### GM-13. 빈 필터 결과 후 stale download 방지

목적:

- 결과가 없는 필터 이후 이전 다운로드 결과가 재사용되지 않는지 확인한다.

절차:

1. 결과가 있는 필터를 실행하고 다운로드 가능 상태를 만든다.
2. 결과가 없는 필터 조건을 실행한다.
3. 다시 다운로드를 호출한다.

기대 결과:

- 이전 필터 결과가 다운로드되지 않는다.
- 현재 세션의 다운로드 대상이 비워진다.

### GM-14. CSV 다운로드 escaping

목적:

- 다운로드 CSV가 표준 CSV escaping 규칙을 지키는지 확인한다.

절차:

1. 쉼표, 따옴표, 줄바꿈 포함 피드백을 업로드한다.
2. 전체 필터를 실행한다.
3. 다운로드 CSV를 확인한다.

기대 결과:

- 쉼표 또는 줄바꿈 포함 필드는 큰따옴표로 감싸진다.
- 필드 내부 따옴표는 `""`로 escaping된다.
- 다운로드한 CSV를 다시 파싱해도 원문 피드백이 보존된다.

### GM-15. 입력 검증 메시지

목적:

- 실패 입력이 성공처럼 보이지 않는지 확인한다.

절차:

1. 공백, 탭, 줄바꿈만 있는 직접 입력을 전송한다.
2. 파일 없이 업로드 요청을 전송한다.
3. 빈 CSV 업로드를 전송한다.

기대 결과:

- 공백-only 입력은 피드백으로 저장되지 않는다.
- 파일 미선택은 `파일이 선택되지` 안내를 표시한다.
- 유효 데이터가 없는 CSV는 성공 메시지를 표시하지 않는다.

### GM-16. HTML escaping

목적:

- 사용자 입력이 HTML 구조를 깨뜨리거나 스크립트로 실행되지 않는지 확인한다.

절차:

1. `<script>alert(1)</script>`와 따옴표가 포함된 텍스트를 입력한다.
2. 응답 HTML을 확인한다.

기대 결과:

- `<`, `>`, `"`는 HTML entity로 escape된다.
- 입력 텍스트가 태그 또는 스크립트로 실행되지 않는다.

### GM-17. 서버 시작 실패

목적:

- 포트 바인딩 실패 또는 listen 실패가 성공으로 처리되지 않는지 확인한다.

절차:

1. fake `httplib::Server::listen`이 실패를 반환하도록 설정한다.
2. main 진입 흐름을 호출한다.

기대 결과:

- 종료 코드는 0이 아니다.
- ERROR 로그에 서버 시작 실패 원인이 포함된다.

### GM-18. 사용자 원문 로그 보호

목적:

- 기본 로그와 stdout에 사용자 피드백 원문이 남지 않는지 확인한다.

절차:

1. 민감 정보가 포함된 피드백을 입력한다.
2. 필터링을 실행한다.
3. stdout/stderr를 캡처한다.

기대 결과:

- 필터링 과정에서 원문 피드백이 stdout에 출력되지 않는다.
- 기본 DEBUG 모드는 비활성화되어 있다.
- INFO 로그는 개수, 처리 결과 같은 메타데이터 중심이다.

## 7. 테스트 자동화 우선순위

### 1순위: 상태와 다운로드

- GM-04 사용자 세션 분리
- GM-11 필터 결과 다운로드
- GM-12 필터 전 다운로드 차단
- GM-13 stale download 방지

이 영역은 사용자 데이터 노출과 잘못된 파일 다운로드로 이어질 수 있어 최우선 자동화 대상이다.

### 2순위: CSV 입출력

- GM-05 정상 CSV 업로드
- GM-06 CSV text 컬럼 위치 변경
- GM-07 헤더 없는 CSV 데이터 보존
- GM-08 CSV quoted field 파싱
- GM-14 CSV 다운로드 escaping

실제 고객 데이터에서 가장 자주 깨질 수 있는 경로이므로 입력과 출력을 함께 검증한다.

### 3순위: 분석/필터 기준

- GM-09 감정 필터 정상 동작
- GM-10 카테고리 필터 정상 동작

분석과 필터 기준이 다시 분리되는 회귀를 방지한다.

### 4순위: 사용자 메시지와 운영 안정성

- GM-15 입력 검증 메시지
- GM-17 서버 시작 실패
- GM-18 사용자 원문 로그 보호

운영자가 실패를 식별하고 사용자가 실패를 성공으로 오해하지 않도록 한다.

### 5순위: 화면 보존

- GM-01 초기 화면 렌더링
- GM-02 단일 직접 입력 분석
- GM-03 여러 직접 입력 누적 분석
- GM-16 HTML escaping

렌더링 리팩토링과 화면 구조 변경 시 사용한다.

## 8. Catch2 테스트 구현 가이드

### 8.1 Fixture 구성

권장 fixture:

- `RouteFixture`
  - fake `httplib` route map 초기화
  - 서버 route 등록
  - 요청/응답 helper 제공
- `SessionFixture`
  - 테스트 시작 전 세션 상태 초기화
  - 테스트 종료 후 세션 상태 초기화
- `OutputCapture`
  - stdout/stderr 캡처
  - 원문 로그 출력 검증

### 8.2 Helper 함수

권장 helper:

- `invokeGet(path, headers)`
- `invokePost(path, body, headers)`
- `invokeUpload(content, headers)`
- `invokeUploadWithoutFile()`
- `contains(haystack, needle)`
- `parseDownloadedCsv(body)`

### 8.3 Assertion 기준

- HTML 전체 snapshot 비교는 피한다.
- 핵심 텍스트 포함 여부와 상태 변화 중심으로 검증한다.
- CSV는 문자열 포함 검증과 재파싱 검증을 함께 사용한다.
- 로그는 전체 로그 형식보다 민감 원문 포함 여부와 로그 레벨 포함 여부를 검증한다.
- 테스트 순서에 의존하지 않도록 각 테스트가 독립적으로 fixture를 구성한다.

## 9. CMake 테스트 타깃 계획

향후 구현 시 CMake에는 다음 타깃을 추가하는 방향을 권장한다.

```cmake
add_executable(feedback_analyzer_golden_master_tests
    tests/golden_master/golden_master_http_flow_test.cpp
    tests/golden_master/golden_master_csv_flow_test.cpp
    tests/golden_master/golden_master_analysis_filter_test.cpp
    tests/golden_master/golden_master_logging_test.cpp
    src/cpp/Constants.cpp
    src/cpp/Filters.cpp
    src/cpp/Logger.cpp
    src/cpp/Session.cpp
    src/cpp/TextAnalyzer.cpp
    src/cpp/UIComponents.cpp
)

target_compile_features(feedback_analyzer_golden_master_tests PRIVATE cxx_std_17)
target_include_directories(feedback_analyzer_golden_master_tests PRIVATE src/cpp)
target_link_libraries(feedback_analyzer_golden_master_tests PRIVATE Catch2::Catch2WithMain)

add_test(NAME golden_master COMMAND feedback_analyzer_golden_master_tests)
```

주의:

- 실제 반영 시 프로젝트의 Catch2 설치 방식과 기존 CMake 정책에 맞춰 조정한다.
- Windows 빌드에서는 기존 앱 타깃과 동일하게 필요한 네트워크 라이브러리 조건을 확인한다.
- fake `httplib` 방식 테스트는 실제 포트를 열지 않도록 별도 컴파일 경계를 둔다.

## 10. 실행 전략

### 리팩토링 전

1. Golden Master 테스트를 먼저 구현한다.
2. 현재 `Refactor` 브랜치 기준으로 전체 Golden Master가 Green인지 확인한다.
3. 실패가 발생하면 테스트 기대값 오류인지 실제 회귀인지 분류한다.

### 각 리팩토링 커밋 후

1. 변경 영역과 직접 관련된 GM 테스트를 실행한다.
2. 전체 Golden Master 테스트를 실행한다.
3. 기존 RED 회귀 테스트도 함께 실행한다.
4. 실패가 있으면 해당 커밋 안에서 원인을 수정한다.

### 리팩토링 완료 후

1. 전체 빌드를 실행한다.
2. 전체 Golden Master 테스트를 실행한다.
3. 전체 RED 회귀 테스트를 실행한다.
4. 필요 시 브라우저 수동 smoke test로 화면 흐름을 확인한다.

## 11. 완료 기준

- Golden Master 테스트가 최소 18개 이상 자동화된다.
- 각 테스트는 독립 실행과 반복 실행에서 동일한 결과를 낸다.
- CSV 입력/출력, 분석/필터, 다운로드, 세션 상태, 입력 검증, 로그 보호가 모두 포함된다.
- CMake `ctest` 또는 명시적 테스트 실행으로 전체 회귀 테스트를 한 번에 실행할 수 있다.
- 테스트 실패 시 어떤 기능 영역의 회귀인지 테스트 이름만으로 식별할 수 있다.

## 12. 남은 리스크와 후속 작업

- 현재 문서는 계획 문서이며 테스트 구현은 포함하지 않는다.
- 실제 Catch2 도입 시 의존성 설치 방식과 CMake 통합 정책을 먼저 확정해야 한다.
- fake HTTP 경계로 검증하기 어려운 실제 네트워크/브라우저 동작은 별도 수동 또는 E2E smoke test로 남길 수 있다.
- 동시성 안전성은 현재 Golden Master보다 더 넓은 범위의 부하/경합 테스트가 필요할 수 있다.
