# Feedback Analyzer 리팩토링 TODO List

## 목적

이 문서는 `Regacy Code 분석 리포트`를 기반으로 Feedback Analyzer C++ 코드의 리팩토링 작업 순서를 정리한 실행 계획이다. 개발자는 이 문서를 기준으로 위험도가 높은 문제부터 작은 커밋 단위로 개선을 진행한다.

리팩토링의 핵심 목표는 다음과 같다.

- 사용자 데이터 섞임과 잘못된 다운로드를 먼저 차단한다.
- 분석 결과와 필터 결과의 불일치를 제거한다.
- CSV 입출력 안정성을 높인다.
- 책임이 과도하게 집중된 구조를 단계적으로 분리한다.
- 테스트 가능한 구조를 만든다.

## 리팩토링 원칙

- 한 커밋은 하나의 명확한 문제만 해결한다.
- 동작 변경이 있는 커밋과 구조 정리 커밋을 분리한다.
- 리팩토링 중 기존 기능의 입출력 흐름을 최대한 보존한다.
- 위험도가 높은 공유 상태, 다운로드, CSV 처리부터 개선한다.
- 각 커밋 후 최소한 수동 검증 또는 테스트 항목을 남긴다.

## 전체 우선순위

| 우선순위 | 리팩토링 영역 | 이유 |
| --- | --- | --- |
| 1 | 다운로드 결과와 필터 상태 정리 | 잘못된 결과 다운로드는 사용자에게 직접적인 오류를 만든다. |
| 2 | 사용자 데이터와 공유 상태 관리 | 다중 사용자 환경에서 데이터 섞임과 동시성 문제가 발생할 수 있다. |
| 3 | 분석 기준과 필터 기준 통합 | 같은 데이터가 화면과 필터에서 다르게 해석되는 문제를 막아야 한다. |
| 4 | CSV 입력과 출력 안정화 | 실제 고객 데이터에서 데이터 유실과 깨진 파일이 발생할 수 있다. |
| 5 | 입력 검증과 오류 메시지 개선 | 실패 상황을 사용자가 성공으로 오해하지 않도록 해야 한다. |
| 6 | 책임 분리 | 변경 영향 범위를 줄이고 테스트 가능한 구조로 만든다. |
| 7 | 테스트 기반 마련 | 이후 리팩토링과 기능 변경의 안전장치를 만든다. |
| 8 | 죽은 코드와 네이밍 정리 | 유지보수자의 혼동을 줄인다. |

## 커밋 진행 시 체크리스트

각 커밋 전 확인:

- 이번 커밋이 하나의 문제만 해결하는가?
- 동작 변경과 단순 정리가 섞여 있지 않은가?
- 변경 전후 수동 검증 시나리오가 있는가?

각 커밋 후 확인:

- 빌드가 성공하는가?
- 기존 핵심 흐름이 깨지지 않았는가?
- 이전 필터 결과나 사용자 데이터가 잘못 재사용되지 않는가?
- 분석 결과와 필터 결과가 서로 납득 가능한가?
- 실패 상황이 조용히 성공으로 처리되지 않는가?

## 최종 목표 상태

리팩토링 완료 후 코드는 다음 상태를 목표로 한다.

- 사용자 데이터와 필터 결과의 소유 범위가 명확하다.
- 분석과 필터가 동일한 판단 기준을 사용한다.
- CSV 입력과 출력이 실제 고객 데이터에 대해 안정적으로 동작한다.
- 요청 처리, 화면 렌더링, 분석, 필터링, CSV 처리가 분리되어 있다.
- 핵심 로직은 자동 테스트로 검증할 수 있다.
- 사용되지 않는 코드와 의미가 불명확한 이름이 줄어든다.
